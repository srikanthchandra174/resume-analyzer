What it does

Recruiters and candidates both ask the same question: how well does this resume fit this job? Resume Analyzer answers it with a REST API. You send one PDF resume and one job description. The service reads the text out of the PDF, asks an LLM to compare the two, and returns a structured result:

FieldWhat it contains
analysisIdID of the saved analysis. Use it to fetch the analysis again later.
matchScore0–100 fit score. The database rejects any value outside that range.
missingSkillsSkills the job asks for that the resume doesn't show.
suggestedImprovementsConcrete edits that would strengthen the resume for this role.
interviewQuestions3–5 questions based on both the resume and the job.
summaryA short paragraph explaining the score.

Every analysis is stored, so you can list past results with the history and recent endpoints.

How a request flows

One call to POST /analyze goes through these steps in order. They're coordinated by ResumeAnalysisService.

  1. Receive the uploadResumeAnalysisController binds the multipart form to ResumeAnalysisRequest. A missing file or a blank job description is rejected here with a 400.
  2. Extract the resume textPdfExtractionService checks the file is a .pdf with type application/pdf, then reads its text with Apache PDFBox 3.
  3. Check the cacheoptionalCacheService hashes resume + job description and looks in Redis. It's off by default (CACHE_ENABLED=false), so local runs skip this step.
  4. Ask DeepSeekAiAnalysisService builds a recruiter-style prompt (resume capped at 2,000 characters, job description at 1,000) and sends it through Spring AI's ChatClient to deepseek-chat.
  5. Parse and validateThe JSON object in the reply is parsed. matchScore is required; any missing lists get empty defaults.
  6. Save to PostgreSQLA ResumeAnalysis row is saved, and the three lists go into their own tables.
  7. RespondThe API returns the result as JSON with the new analysisId.

Architecture & data

Code layout

All code lives under com.srikanth.ai.resumeanalyzer.

PackageRole
controllerREST endpoints under /api/v1/resume-analysis
serviceCoordination, PDF extraction, AI prompt and parsing, cache
entity / repositoryJPA entity ResumeAnalysis and its Spring Data repository
dtoRequest, response, history and error payloads
exceptionCustom exceptions plus GlobalExceptionHandler, which turns errors into JSON
configChatClient, Jackson and Redis beans

Database tables

TableHolds
resume_analysisFile name, resume text, job description, match score (0–100 check), summary, timestamps
missing_skillsOne row per missing skill, linked by analysis_id
suggested_improvementsOne row per improvement
interview_questionsOne row per question
analysis_audit_logAudit trail table, created by init-db.sql

Hibernate creates the core tables when the app starts. init-db.sql also adds full-text indexes, an updated_at trigger and the audit table.

Run it locally

You'll need JDK 21, PostgreSQL 16 or newer, and a DeepSeek API key. Docker and Redis aren't required.

1. Create the database

In psql or pgAdmin, connected as the postgres superuser:

CREATE USER resumeuser WITH PASSWORD 'resumepassword';
CREATE DATABASE resume_analyzer OWNER resumeuser;

2. Apply the schema (optional)

psql -U resumeuser -h localhost -d resume_analyzer -f init-db.sql

3. Save your DeepSeek key

Run this once. It's saved to your Windows user account, so open a new terminal afterwards for it to take effect.

setx DEEPSEEK_API_KEY "sk-your-deepseek-key"

4. Start the app

cd D:\Srikanth\ProjectstoCommit\resume-analyzer
.\mvnw.cmd spring-boot:run

It's ready when the log shows Started ResumeAnalyzerApplication, usually within 10 seconds. Keep this window open, and press Ctrl+C to stop.

Test with Postman

All endpoints share the base URL http://localhost:8080/api/v1/resume-analysis. Use the Postman desktop app: the browser version can't attach local files unless you install the Postman Desktop Agent.

Health check

GET http://localhost:8080/api/v1/resume-analysis/health
200 OKPlain text: Resume Analyzer API is up and running!

Analyze a resume

POST http://localhost:8080/api/v1/resume-analysis/analyze

Open Body → form-data and add two keys, spelled exactly as shown. To make resumeFile a file, hover over the right edge of its Key cell and switch the hidden Text dropdown to File.

none form-data x-www-form-urlencoded raw binary
KeyTypeValue
resumeFileFileSelect Files → resume.pdf
jobDescriptionTextPaste a job description (samples below)

Leave the Headers tab alone. Postman sets multipart/form-data with the right boundary itself, and a hand-typed Content-Type header breaks the upload.

Get one analysis

GET http://localhost:8080/api/v1/resume-analysis/{id}

Replace {id} with the analysisId from the analyze response, e.g. /1.

200 OKThe same fields as the analyze response

Analysis history (paged)

GET http://localhost:8080/api/v1/resume-analysis/history?page=0&size=10&sort=createdAt,desc

All three query parameters are optional. The defaults are page 0, 10 per page, newest first.

200 OKA page object. Results are in content, each with id, fileName, matchScore and createdAt (epoch milliseconds). The total is in totalElements.

200 OKA plain list of analyses created within the last hours hours (default 24)

Demo script

A 5-minute run-through for showing the project to others. Start the app and open Postman before you begin.

  1. Show it's alive. Send Health check to show the API responding.
  2. Run a strong match. Analyze a Java resume against the Junior Java description. Point out the high score and the short missing-skills list.
  3. Run a stretch match. Send the same resume against Senior microservices. The score drops, and Kubernetes, Kafka and Spring Cloud appear in the missing skills.
  4. Show the coaching output. Read out one suggested improvement and one interview question. Both are specific to this resume, not boilerplate.
  5. Show it's stored. Send History to see both runs, then Get one analysis with an ID from the list.
  6. Show the guard rails. Send analyze with no file to get a clean 400, and get ID 99999 to get a 404.

Limits & notes

  • Text-based PDFs only. Scanned or image-only resumes have no text for PDFBox to read, so they fail or score poorly. Export from Word or Google Docs instead.
  • Long inputs are cut off. Only the first 2,000 characters of the resume and 1,000 of the job description reach the model.
  • Scores vary a little. The model runs at temperature 0.7, so repeating the same request can give a slightly different score and wording.
  • Every run is saved. With caching off (the local default), repeating a request calls DeepSeek again and adds a new row.
  • Cached results have no ID. With Redis caching on, a cache hit returns the result without an analysisId and doesn't save a new row.
  • No authentication yet. The API is open and allows requests from any origin (CORS), so run it only on your own machine or a trusted network.
  • Semantic search is planned, not built. init-db.sql contains a commented-out pgvector section, but nothing generates embeddings yet.
